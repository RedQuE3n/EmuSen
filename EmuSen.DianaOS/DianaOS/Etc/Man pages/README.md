# Man pages — index

EmuSen's documentation set: project status, architecture, the debug toolchain, settings, and per-hardware reference notes. This page exists purely to help you find the right doc without opening all of them - it doesn't duplicate their content.

The general, top-level docs listed below now live in `EmuSen.DianaOS/DianaOS/Usr/Home/Documents/EmuSen Manual/`, not alongside this README - only `Hardware/` and `Old/` (below) actually live in this `Etc/Man pages/` folder itself.

- **`EmuSen_Debugging_Tools_Reference_v5.md`** — every debug tool: console hotkeys, `DebugSettings` logging flags, and the full DianaOS shell/command reference (the reusable, core-agnostic debug toolchain). The largest doc here - organized top-down from "things you press a key for" to "the underlying toolchain." Read **§3.45** before using the reference probe: it is no longer Mesen-specific (a policy layer plus a backend per emulator, including a libretro backend that drives any core), and **§3.45a** records that every dump the probe took before 2026-08-06 was read out of a *running* emulation thread - which retires claims in §3.39 and §3.40. **§3.50** is the Rust port and why Mesen's own C ABI could not close the gap; **§3.52** is what replaced it - an add-only `probe-c-api.patch` giving Mesen a probe ABI of its own, after which the whole probe is `Reference/probe-rs/` and `Reference/probe/` is gone. Read §3.52 for the current shape and §3.50 for the reasoning behind it. **§3.51** is what a dump set costs on disk. **§3.46** is `apudiff` and the three-emulator SMB3 result. **§3.53** is where the "the policy layer names no emulator" claim turned out to be false in twenty places, what the guard test that now enforces it does and does not catch, and the `gsudiff.py` format drift found while auditing the consumers. **§3.54** is the three-host development story — Linux, macOS and Windows: the emulator was already portable and the *toolchain* was not, the host table that replaced a chain of per-host branches, a capability matrix saying what each host can actually do, why Windows can have the libretro backend but **not** the Mesen one (Mesen's MSVC projects list their sources so the add-only patch is never compiled, and a PE import cannot express a relative load at all), what the Fedora "nothing is installed" trick could and could not carry over — and, at the end, exactly which claims are still unverified and on which host. **§3.55** and **§3.56** are the test suite's cost: 69% of a six-minute run was one class replaying the same dump-set frames from boot for every assertion, which is arithmetic rather than scheduling — read §3.55 before assuming a slow suite wants more threads, and §3.56 for the two collections that are the only things standing between the suite and full parallelism, plus the `CpuBinaryTrace` process-wide-singleton crash that enabling it found.

## The "This revision / Previous revision" convention

Several docs above (notably `EmuSen_Debugging_Tools_Reference_v5.md` and `EmuSen_Frontend_Driver.md`) open with an italicized paragraph chaining "This revision: ... Previous revision: ... " notes - a lightweight, inline changelog covering what's changed recently, kept short enough to skim before reading the rest of the doc. Not every doc uses this (`EmuSen_Core_Gameplan.md`, `Commands.txt`, and others don't) - it's a convention available when a doc's own history is worth surfacing inline, not a requirement. When one of these preambles grows long enough to stop being skimmable, trim the older entries down to a short summary line each and point to `git log` for full detail, rather than letting it grow unbounded - full reasoning/diffs for anything old enough to be compressed already lives in commit history.

# EmuSen — Games Tested

*(Living document — tracks real-game compatibility testing across EmuSen's cores, separate from the CPU/PPU ground-truth test suites in `EmuSen.Tomoe`. Those prove individual opcodes/registers match hardware in isolation; this tracks what actually happens when a real, complete commercial ROM is played.)*

---

## 1. Rating scale

Five categories, most to least playable:

- **Perfect** — no known issues. Plays exactly as expected, start to finish.
- **Good** — mild issues. Small, cosmetic, or easily-worked-around problems that don't affect actually playing the game.
- **Fair** — moderate issues. Noticeable, real bugs (visual glitches, incorrect behavior in specific scenes/mechanics) that don't block progress but are clearly wrong.
- **Bad** — severe issues. Bugs serious enough to meaningfully interfere with playing normally (frequent crashes, broken core mechanics, major visual corruption).
- **Unplayable** — doesn't boot, crashes immediately/consistently, or is broken badly enough that it can't be played at all.

A game's category reflects its *current* state, not a permanent verdict — entries move up as bugs get fixed (or down if a fix regresses something else). Each entry links to the relevant hardware doc section(s) for the technical detail behind the rating, rather than duplicating it here.

## 2. Venus (SNES)

### Good

- **Kirby's Dream Land 3** — **was Unplayable (black screen), now plays.** The first coprocessor game this core runs: map mode `$23`, cartridge type `$35` — a genuine **SA-1**. With no SA-1 emulation the S-CPU still ran, but everything the chip was meant to compute stayed zero, including the buffer holding the decompressed SPC700 sound driver; the S-CPU uploaded 64KB of zeroes to the APU and then parked forever at `$00:DEAC` (`LDA $2140 / BNE`) waiting for a sound driver that never signalled ready, leaving `INIDISP` in forced blank with VRAM/CGRAM/OAM all still zero. Fixed by implementing the SA-1 — second 65C816, Super MMC banking, I-RAM/BW-RAM, the control/message/vector registers, timer, arithmetic unit, variable-length bit stream reader, and normal DMA; see `Hardware/Nintendo/Venus - SNES/Venus_SA1.md`. Verified headless: HAL logo → intro cutscene → title screen → level 1 gameplay, all rendering correctly, with the sound driver uploading properly and save states round-tripping byte-identically. Rated Good rather than Perfect because coverage stops in the first level, and because **character-conversion DMA is not implemented** (`Venus_SA1.md` §8.1) — this game never requests it, but a game that does will get wrong tile data.

- **Kirby Super Star** — the second SA-1 game, and the one that confirmed the chip work generalises beyond the ROM it was developed against: it booted correctly on the first run with no further changes. Verified headless: the Kirby-on-a-star intro renders in Mode 7, and the "Spring Breeze" sub-game title card renders correctly. Notable for using the SA-1's I-RAM as the S-CPU's direct page (`D = $3700`), which exercises the shared-I-RAM decode from the S-CPU side rather than the SA-1's. Rated Good rather than Perfect because coverage stops at the sub-game select.

- **Donkey Kong Country** — **was Unplayable (black screen), then Fair (booted but sprites were unusable), now plays.** Two fixes got it here. First, HiROM: not a coprocessor game despite the look — cartridge type `$02` (ROM + RAM + battery), Rare's pre-rendered SGI artwork is ordinary compressed tiles needing no special silicon, just a big ROM (`Venus_Memory.md` §2.1a). Second, the OAM address reload: DKC never rewrites `$2102`/`$2103` after setup and DMAs all 544 OAM bytes to `$2104` every frame, relying on hardware reloading the write pointer at vblank. Without that reload the upload landed two bytes late and Donkey Kong rendered as fragments scattered across the screen — see `Hardware/Nintendo/Venus - SNES/Venus_PPU.md` §6.4. Verified headless: intro → title → mode select → map → Jungle Hijinxs, with DK walking, jumping, and enemy/collectible sprites all correct. Rated Good rather than Perfect because only the first level's opening has been exercised.

- **Donkey Kong Country 2** — **was Fair (stopped on the region lockout screen), now plays.** The local `DKC2.smc` is a European dump (header country byte `$02`), and the game reads `STAT78` (`$213F`) bit 4 to identify the console; the core hardcoded that bit to NTSC, so the cartridge correctly refused to run — exactly what a PAL cart does in an NTSC console on real hardware. Fixed by adding genuine PAL support rather than faking the bit: region is classified from the country byte (`Venus_Memory.md` §2.5) and drives 312-scanline/21281370 Hz timing and the `STAT78` bit together (`Venus_CPU.md` §8.5c). `perf` confirms the core reporting a 20.00 ms/frame budget at **50.01 Hz**, comfortably met (mean 1.90 ms, 0/200 frames over budget). Verified headless: Rare logo → Nintendo Presents → title → Select Game → player-count menu → Gangplank Galleon map → Pirate Panic, with Diddy running and jumping, the banana/life HUD counting up, enemies and the DK barrel rendering, parallax rigging scrolling, and audio playing throughout. Rated Good rather than Perfect because coverage stops in the first level.
  - Note for anyone scripting this game: the player-count menu and the map take **A**, not Start, and the level-name card is dismissed with **B** (it did not auto-advance in 1800 frames / ~36 s of waiting, which is worth a hardware comparison at some point but did not block anything).
  - **A second, unrelated bug fell out of testing it**: Pirate Panic parks BG2 at `VOFS = $3FF` (i.e. -1), which exposed a one-row vertical-scroll off-by-one affecting *every* game — the top display row wrapped to the tilemap's last row instead of its first. Fixed; see `Venus_PPU.md` §2.4. It also removed a one-pixel seam partway down this game's Gangplank Galleon map and the black top row on Donkey Kong Country's mode-select screen.

- **Illusion of Gaia** — boots, plays, and reaches gameplay correctly: Enix/Nintendo logos → title → file select → the School opening scene with dialogue advancing, audio playing throughout. **No emulator bug** — an earlier session spent a long investigation chasing one that did not exist, so the finding is worth recording. Its title screen does not accept Start until roughly **frame 1071** (~18s after boot), because the game's own script thread only reaches its "wait for button" step then; every earlier press does nothing, which looks exactly like dead input. The suspicious-looking WRAM `$065A` mask (`0xFFF0`, masking every button out of `$0656` at `$82:818B`) is a **red herring**: it correctly gates the *processed* pad word during the intro, and the title's Start check doesn't use `$0656` at all — script command `COP #$40` (handler `$80:94D5`) tests `BIT $0660`, the raw unmasked pad word. Rated Good rather than Perfect only because coverage stops shortly after the opening scene.

- **Secret of Mana** — boots and plays; title → file select → name entry → prologue → gameplay all render correctly. **One real bug found and fixed**: its file-select and name-entry menus are drawn entirely in **Mode 5** (true hi-res), which this core rendered by sampling 8 consecutive columns of a single tile per 8 output pixels instead of mapping each of the 512 dots to its own BG column across a paired 16-dot cell. Result was sliced, half-missing glyphs — "GAME SELECT" rendered as "GME SEET" — and see-through window frames. Fixed by implementing true Mode 5/6 BG fetch; see `Hardware/Nintendo/Venus - SNES/Venus_PPU.md` §8 (Phase B) for the model and the one open parity question. Rated Good rather than Perfect because coverage stops at the opening prologue.

### Bad

- **Yoshi's Island (Super Mario World 2)** — **was Unplayable (black screen); the intro, title screen and file menu now all render correctly.** The first SuperFX game: cartridge type `$15`, a GSU-2. The chip is implemented — memory map, the full instruction set, the plot hardware — and it executes genuine game code: the intro's bordered frame and its GSU-rendered interior, then the title screen's 3D island and the rotated island behind the file menu. Six real bugs were found and fixed getting here, all documented in `Hardware/Nintendo/Venus - SNES/Venus_SuperFX.md`: the R15 pipeline invariant (§4.1 — the game's `WITH R15 : TO R13` loop idiom is what pins it), the OBJ-mode tile order (§6.2), the screen-height bit order (§6.1a — the title screen's island was vertical smears until it was corrected), and Game Pak RAM sizing (§1 — the header under-reports it and wrapping writes crashed the S-CPU into zeroed WRAM). Rated Bad rather than Unplayable because it genuinely boots and renders; still pending a real play session past the file menu.

  - **The striped strip below the frame is fixed (2026-08-03), and it was never a SuperFX problem.** For scanlines 152-197 the game HDMAs `BGMODE` to Mode 0 and `TM` to `$08`, drawing the story text with **BG4 only** (tilemap VRAM `$F800`, chars `$E000` — the `$70:4C00` page `7E:C8AF` uploads). Two core bugs hid it. First, the game enables `$420C` at scanline 12 and clears it at 198, so it is never set at scanline 0 and this core — which armed HDMA only there — ran **zero** HDMA transfers in 700 frames against 415 enable writes (`Venus_Memory.md` §3.2a). Second, Mode 0's per-layer CGRAM blocks were unimplemented, so BG4 palettes 6/7 read CGRAM 24-31 and the text came out dark red instead of white (`Venus_PPU.md` §14). The intro now reads "A long, long time ago..." and "...and races towards the stork with blinding speed." correctly.
  - **Root-caused and fixed.** The S-CPU's `$6000-$7FFF` Game Pak RAM window was bank-indexed instead of mirroring the first 8KB into every low bank (`Venus_SuperFX.md` §10.0). The game reads a jump-table index through `$0F:6F0C`; the wrong offset returned an odd value, the odd index misread a 16-bit pointer table, the `PHA`/`RTS` dispatch landed one byte before a real instruction boundary, and the resulting stray `PLY` corrupted the stack until an `RTS` returned into zeroed WRAM. It now runs past the old frame-1759 crash with output still changing at frame 4500. **Still rated Bad pending a real play session** - nothing beyond "it no longer crashes and keeps drawing" has been verified yet.
  - **The intro now renders correctly (2026-08-02).** A branch was clearing the GSU's prefix state before its delay-slot instruction ran; branches are the one non-prefix instruction that must not (`Venus_SuperFX.md` §4.2, §10.4). The game's RLE blitter has `FROM R6 : TO R5 : ALT2 : BRA $8106` with `AND #15` in the delay slot, so the fix restores both the run colour and the bit-stream buffer the wrong decode was clobbering. Measured on the blitter's own invariant, not by eye: plots at x >= 128 went 10,347 -> **0**, `PLOTMAXX` `$FF` -> **`$7F`**. The Nintendo-logo quilt, the sunrise page and the cloud page all draw correctly through frame 6000.
  - **Retired, and worth knowing why it cost four rounds.** The strip was chased as "18 BG3 tiles (`$1A1-$1A9`, `$1B1-$1B9`, VRAM `$FA10-$FBA0`) that the tilemap references and nothing uploads". That is all true and all irrelevant: `$FA10` is inside BG4's tilemap, and BG3 is switched off over those scanlines, so hardware never reads it. The `$0130` fill is a tilemap clear, not a missing upload. `layers bg3` did correctly place the strip on BG3, but it masks a layer for the whole frame and so cannot see a mid-frame `TM` change — **`scanregs all` over the failing rows is the check that settles which layer is live, and it belongs before tracing where any layer's data comes from.** `Venus_SuperFX.md` §10.5 has the full retraction.
  - The failure that led there was measured precisely (`Venus_SuperFX.md` §10.1): at **frame 1759** the S-CPU derails into `$7E:0E6A` — zeroed WRAM, where `$00` is `BRK` — wanders, and by frame 1765 is in emulation mode parked at `$00:814F` with the screen in forced blank. Output is byte-identical from then on. The GSU is still working right up to the crash (Game Pak RAM changes across the window, `Running = 1` at 1750), so **the S-CPU dies first and the GSU stops afterwards** — not the reverse. This is the *same* crash-into-zeroed-WRAM bug the RAM-sizing fix was thought to have cured; it was only pushed later, from boot to frame 1759.

  Two earlier investigations (`LJMP`'s operand direction, the `ALT3` decodes) were spent on instruction-set details on the assumption the S-CPU kept running normally and was merely consuming bad GSU output. That assumption was wrong, and both features turned out to be unreachable in this game.

### Fair

- **Super Mario World** — the coins/Yoshi rendering bug this entry used to describe is **fixed** (confirmed by the user 2026-08-01). What remains recorded against the game is a glitch when the overworld map's hills rise and grow. The old narrowing work (the `$7E8000-$7E97FF` staging buffer, the `$0D80-$0D9F` job table, `EmuSen_Core_Gameplan.md` §1) is history, not an open thread — do not restart from it.

  **Boot and title screen re-checked in detail on 2026-08-02 and found correct.** A headless sweep of frames 0–3000 (`--autoshot`, then a neighbour-difference scan for one-frame transients) shows: black, "- Nintendo -/Presents" fading in and out, the title fading in, the circular iris opening onto the level backdrop, the attract demo, and the file-select/player-count menus and overworld after `tap Start`. No missing layer, no transient glitch frame, nothing out of place.

  One thing that *looks* like a defect and is not, recorded so it does not get re-investigated: the small BG2 cloud at the top left of the title screen has two 1×4-pixel black marks in it. The full chain was verified byte by byte — BG2 tilemap entry `13B4` at row 26 col 3 (tile `$13B`, palette 4), VRAM tile bytes at `$2760`, the `$00:AACD` 3bpp→4bpp uploader that wrote them, the source buffer at `$7E:B288`, and the LZ2 decompressor at `$00:B888` that filled it from the compressed stream at `$0A:BF54`. Hand-decoding that stream (`23 FF` byte-fill ×4, `43 00 FF` word-fill ×4, `47 11 FF` word-fill ×8) reproduces the emulator's output exactly, and palette 4 index 3 is written black by the game itself from `$00:9245`. The marks are in the cartridge. See `EmuSen_Debugging_Tools_Reference_v5.md` §3.25/§3.26 for the two tools (`memfind`, `bp write`) that made that chain traceable.

- **Super Mario All-Stars** — reported symptom: no controller response once past each embedded game's title screen, except Super Mario World. Root-caused, **not an EmuSen bug**: SMAS's classic NES-style sub-games (SMB1, SMB2/Lost Levels, SMB3) read Controller 2 for input, not Controller 1 - a real, independently-documented quirk of the actual cartridge (other emulators, e.g. PocketSNES, have hit the same thing; native SMW correctly reads Controller 1). Confirmed directly against this core: on the Select Game menu, every Player 1 button except D-pad scrolling did nothing, while a single Player 1-equivalent press sent as Player 2 (`EmuSen.Pharaoh --tap2`) immediately advanced to File Select. Workaround now built in: a mirror-Player-1-to-Player-2 toggle (`EmuSen.Hotaru`: F7 hotkey, a per-`GameWindow` flag; `EmuSen.Mistress`: checkbox in Controller Settings), off by default so it doesn't affect real two-player sessions in other games. Not yet verified all the way into actual SMB1 gameplay with the mirror on (headless testing got to File Select but not further before this was written) - the menu-level finding is strong evidence, not a full confirmation.
  - A separate, independently-real bug found during the same investigation: `Input.WriteStrobe()` seeded the manual `$4016`/`$4017` shift registers from the previous frame's auto-joypad latch instead of the live button state, contradicting its own doc comment. Fixed, but not confirmed to be related to this game's symptom specifically.

- **The Legend of Zelda: A Link to the Past** — real, reproducible bugs found during testing, none of them blocking progress:
  - Stuck overworld subscreen ("yellow bar"): closing an item-get dialog (e.g. the Lamp chest) can leave WRAM `$1D`/`TS` stuck enabling BG1 on the subscreen outdoors, permanently color-math-blending a torch overlay tile into the overworld as a solid yellow band. Root cause and investigation history (including two reverted fix attempts) in `Hardware/Nintendo/Venus - SNES/Venus_PPU.md` §12.1. Still open, unpatched.
  - Missing rain overlay: the overworld storm-intro rain doesn't always render on a fresh save, and on other saves can appear briefly then disappear while walking. Root-caused as far as BG3's raindrop tilemap not being consistently populated/maintained in VRAM. Not yet root-caused further. Details in `Venus_PPU.md` §12.2.
  - (Fixed, no longer an issue as of this testing pass) Picking up the Lamp from a chest showed the "You got the Lamp!" dialog but the item never entered permanent inventory — root-caused to a 65816 CPU emulation bug (opcode `0x87`, `STA [dp]`, wired to the wrong addressing-mode function), fixed and verified against ground-truth CPU test vectors.

- **Super Metroid** — **was Unplayable (boot hang), now boots.** The hang before the title screen is fixed: the IPL ROM was stamped into APU RAM rather than overlaid read-only above it, so the game's own audio-engine upload into `$FFC0-$FFFF` overwrote the boot code mid-execution. Full root-cause writeup in `Hardware/Nintendo/Venus - SNES/Venus_APU.md` §2.7, hardware model in §1.1. Verified headless over 60 seconds: Nintendo logo → Ceres cinematic → title screen → attract-mode demo, with the SPC700 running Super Metroid's own audio engine at `$1500` instead of sitting in the IPL. **Actual gameplay is not yet verified** — nothing past the attract demo has been exercised, so this Fair rating is provisional and based only on the boot sequence rendering correctly; it needs a real play session (and an audio check) before it can be trusted or moved up.

- **Donkey Kong Country 3** — boots and reaches its title screen (fixed by the same HiROM work as DKC — see `Venus_Memory.md` §2.1a). Gameplay not yet verified.

## 3. Moon (NES)

**Coverage across the local set:** 2,963 of 3,536 ROMs (**83.8%**) boot four frames clean, up from 59.0% before MMC3 and the four simple boards. Every remaining failure is a named `NotSupportedException` for an unimplemented mapper, not a crash — see `Hardware/Nintendo/Moon - NES/Moon_Memory.md` §4.

### Good

- **A Boy and His Blob: Trouble on Blobolonia** — the first real commercial ROM this core ran, and the proof the CPU/PPU/mapper work holds up outside synthetic fixtures. MMC1 (iNES mapper 1), 128 KB PRG + 128 KB CHR. Verified headless through Pharaoh: title screen renders correctly (logo art, colour, and the copyright/licence text), Start reaches gameplay, and the opening Blobolonia street scene draws the boy, Blob, the house, the parallax city skyline and both HUD bars. Holding **Right** walks the character and scrolls the camera, streaming new CHR banks in as it goes. **Audio works** — a WAV capture of the title music reads peak 7797 with the DC offset filtered out. Rated Good rather than Perfect because coverage stops at the opening screen.

- **Super Mario Bros. 2** — **was Unplayable (mapper 4 unimplemented), now plays.** MMC3. Boots to the curtain screen and advances to "PLEASE SELECT PLAYER" on Start, with working audio. Rated Good rather than Perfect because coverage stops at the character select.

- **Super Mario Bros. 3** — **was Unplayable, now plays, but silent.** MMC3, and the game that exposed the pre-render-line A12 bug: its status-bar split landed one line off and corrupted a band of the title screen until the pre-render clock was added (`Moon_Memory.md` §4.6a). Now reaches the World 1 map with the split rendering correctly. **Rated Good only on picture: it produces no sound at all.** The game writes `$4017` once and then never touches `$4000-$4013`, so its sound engine is not running — which is a CPU or mapper question rather than a synthesis one, since SMB2 on the same board has audio. Open issue, see `Moon_APU.md` §6.

- **Super Mario Bros. + Duck Hunt** — **was Unplayable (mapper 66 unimplemented), now boots.** GxROM. Reaches the Super Mario Bros. title screen. Silent there, which is correct — SMB1's title has no music until a game starts. Duck Hunt itself additionally needs the Zapper, which nothing in the input contract models (`EmuSen_Input.md` §6).

- **A Boy and His Blob** — audio now works; see the entry above, which predates the APU.

## 4. Notes on methodology

- Testing uses `EmuSen.Pharaoh` (scripted, reproducible: save states, `--tap` input sequences, screenshot capture, per-pixel/register diagnostics) plus live interactive play via `EmuSen.Hotaru` for anything that needs real-time feedback (precise movement/navigation, timing-sensitive input) that scripted input can't easily reproduce.
- A bug found and fixed gets *removed* from a game's list of open issues, not just annotated — this document should always reflect current, real behavior, checked against the actual running build, not a historical changelog. (Changelog-style history belongs in commit messages and the hardware docs' own investigation writeups, not here.)
- "No known issues" (Perfect) means no issues found *in what's been tested*, not a formal claim of full-game coverage — most games here have only had specific scenes/mechanics exercised, not a full playthrough.

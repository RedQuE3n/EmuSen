# Mars (Nintendo 64)

What exists is a plan: [`Mars_Gameplan.md`](Mars_Gameplan.md), pinned 2026-09-15, which is the "what should I work on next" doc for Mars in the same role `Mercury_Gameplan.md` plays for Mercury — with the difference that it was written before any code rather than during it, and says where it expects to be wrong.

Two decisions are already taken and carry their reasoning there: the whole RCP is emulated at low level (§2.1), and correctness leads with performance as its own later phase (§2.2). §3 is the oracle question — what a Nintendo 64 core can be graded against — and it carries the one unverified assumption the phase order rests on.

[`Mars_References.md`](Mars_References.md) is the second page here: four GPL emulator codebases checked out for study, the procedural rule that keeps them read-only (§2 — they are read for mechanism, and the implementation is written from hardware documentation), what each is actually good for, and §5, which is the record of what they got *wrong*. That last section is the one that fed back into the plan.

[`Mars_TestOracle.md`](Mars_TestOracle.md) is what the plan's §3 was waiting on: the hardware test corpus can report a text verdict headlessly, so the phase order stands. It carries the protocol, the four things Mars must do before the ROM will say a word — two of which fail silently if got wrong — and the finding that the RDP has no hardware-grounded oracle anywhere, only a very good software one.

[`Mars_Documentation.md`](Mars_Documentation.md) is the assessed source list — which documents are authoritative, where they contradict each other, where one of them is outright wrong, and what an implementer needs that no document anywhere answers. Two gaps there shape the work: the RDP's subpixel-mask rule, and system timing in its entirety. It also settles the plan's §2.1 condition by showing the condition was posed wrongly.

[`Mars_Rom.md`](Mars_Rom.md) is the first page describing code rather than plans: Phase 0's container handling and header parser, which emulate nothing. Read §1.1 before touching the loader — the container is decided by the magic word and never by the extension, and the reason is a documented disagreement between sources about what the extensions mean.

[`Mars_Memory.md`](Mars_Memory.md) is Phase A's first slice: the address map, the debug port, and the single machine clock. §3.1 carries the decision that `Count` is derived rather than incremented, which is this project's answer to a failure mode another emulator's commit log documents over years. §2.4 is the one place the CPU's stores are not byte-precise: the RSP's memories take only whole words. §7 became Phase E's cartridge transfer engine: §7.3 is the block walk that decides which bytes land, and §7.6 says which of its rules the corpus actually pins — the rest came from an FPGA core and an emulator fitted to the same corpus, which is a different kind of evidence, and §7.4 names the one size where the corpus's own model and the walk disagree. §7.7–§7.8 are the cartridge bus as the processor sees it — a store the PI keeps once and lets decay, and reads that cannot reach every other halfword — and §7.7 is also the one place the harness's verdict channel is deliberately not the console. §8.3–§8.5 are the MI's mode register, the repeat it arms — one store written across up to 128 bytes, which only the FPGA core among the references implements — and the RDRAM registers, which read a table the corpus measured rather than a register model, because Mars's boot never initialises RDRAM for a model to record.

[`Mars_Cpu.md`](Mars_Cpu.md) is the VR4300's integer core: the dispatch shape, 64-bit registers, the two-program-counter delay-slot model, and the two decisions taken in advance — exceptions are thrown so that a faulting instruction cannot leave partial state (§4), and only cycle counts the vendor manual tabulates are charged (§5).

[`Mars_Tlb.md`](Mars_Tlb.md) is address translation for the mapped segments: paired entries, the linear scan, and §3's three distinct failures — a miss, an entry that is invalid, and a store to a page that is not writable — which vectoring had previously been unable to tell apart. §1.1 is a page-size bug that was invisible to every test that built pairs the ordinary way, and §7 is what an entry actually keeps of the registers written to it, which is less than they hold and normalised in ways the field layout does not predict.

[`Mars_Boot.md`](Mars_Boot.md) is the handoff that replaces the PIF, and the record of what happened when a real ROM ran through it: the corpus boots through libdragon's bootcode into its own entry point, and stops at a coprocessor-1 move, which is where Phase B begins. §6–§8 (2026-09-18) are the cartridge's security chip: how the boot code names it, the seed it hands IPL3, what IPL2 leaves that the 6105's boot code reads, and the 6105's challenge. §8 is why Ocarina of Time did not boot — two registers nobody had set, found at its third instruction, not either of the two things predicted.

[`Mars_Cop0.md`](Mars_Cop0.md) is what the oracle found once it could speak: coprocessor zero is almost nothing but special cases — write masks, constants, registers hardware fills in, and seven that are not registers at all but a latch holding the last COP0 write. §1 is the headline: with this slice every CPU, COP0, TLB, exception and LL/SC test the corpus runs now passes, which is the condition `Mars_Gameplan.md` §4.1 set for Phase A.

[`Mars_FpuMath.md`](Mars_FpuMath.md) is Phase B's body: the software float, and the measurements that justify it having been written rather than borrowed from the host. §1 settles the reversed NaN convention, §3 records that the part refuses to compute with denormals at all, §4.1 settles a rounding question the survey left open, and §8 is a square-root bug that passed every tidy test value. §10 is two commercial cartridges running twenty million instructions without a fault.

[`Mars_Fpu.md`](Mars_Fpu.md) is Phase B's first slice: the coprocessor register files and the paths into them, with no arithmetic at all. Read §9 first — with this in place the hardware corpus starts printing verdicts, and the tally it prints is now a ratchet in the test suite. §9.2 is two integer defects the corpus found and that slice deliberately did not fix; `Mars_Cpu.md` §14 is where they were settled, and neither turned out to be what it looked like.

[`Mars_Privilege.md`](Mars_Privilege.md) is the VR4300's three modes: how the mode is derived — §1, where the answer is that the mode field is not what decides it — and §2's address map, which is three different maps chosen by mode and is kept row for row from the corpus's own forty-five case table. §4 is the asymmetry worth knowing before implementing it: kernel mode runs the doubleword instructions with its own 64-bit addressing bit clear, and the other two modes do not. §6 works out the rule for reverse-endian addressing, which is the next thing the corpus asks for and which nothing yet implements.

[`Mars_ReverseEndian.md`](Mars_ReverseEndian.md) is `Status.RE`, the bit that lets a big-endian processor run little-endian user code. §2 is the whole feature — one exclusive-OR, settled against the corpus's twenty-four result rows rather than read off its helper function, because the obvious reading is right for aligned accesses and wrong for the merging ones. §4 is the part that is easy to leave out (instruction fetch is mirrored too) and §5 is the TLB defect the feature's test harness exposed, which is what five of its seven corpus tests were actually failing on.

[`Mars_Rsp.md`](Mars_Rsp.md) is Phase C's first slice: the signal processor's scalar half, which is MIPS with no exceptions, no alignment and no 64-bit words. §3 and §4 are the two places carrying the main CPU's code across would have been wrong in ways no main-CPU test could catch; §5.1 is a status-register rule the corpus measures for every field; §6 explains why an unbuilt vector instruction does nothing rather than stopping the machine, which is the opposite of the choice made for the FPU and for a reason.

[`Mars_RspVector.md`](Mars_RspVector.md) is Phase C's second slice: the RSP's vector unit, implemented from the models the corpus carries beside its tests rather than from its expected values alone — §0 says which parts came from which. Read §2 before touching the dispatch (every source is copied out before anything is written), §4 and §5 before touching a load or store (loads stop at the register's end and stores wrap), and §6.1 for the one place the corpus contradicts itself and which half was followed.

[`Mars_Microcode.md`](Mars_Microcode.md) is Phase C's second condition — commercial microcode running to a display list — and the finding that closes the phase: Wave Race 64 gets there, but only once the harness stands in for the video and serial interrupts, because no game submits microcode before those Phase E devices have spoken. §3 says exactly what the stand-ins are and are not; §5 is what the plan missed.

[`Mars_Rdp.md`](Mars_Rdp.md) is Phase D's first slice: the display processor's registers, the command stream they deliver, and the fill cycle in whole pixels. Read §0 first — it is the ledger of which rules the corpus measured, which came from community documentation, and which are readings of the reference rasterizer that nothing has graded yet. §5.2 is the pixel-edge rule in that last group, visible as one column and one row in a commercial depth buffer, and §8 is Wave Race's first list carried out. §11 is the picture at a multiple, and §11.2 the copy-mode step that drew Super Mario 64's and Kirby 64's HUDs four times too fast along their texels there.

[`Mars_RdpChromaKey.md`](Mars_RdpChromaKey.md) is Phase D's eleventh slice: chroma keying — the key a primitive measures its colour against, which becomes the pixel's alpha while the cycle's first input becomes its colour. Read the note above §0 before anything else: parallel-rdp does not implement keying at all, so this is the first slice with **no cross-check**, and §3 says exactly what its evidence is and is not.

[`Mars_RdpCopy.md`](Mars_RdpCopy.md) is Phase D's tenth slice and the last of its cycle types: the copy mode — four texels fetched a group and written to the colour image as bytes, with no combiner, blender or depth — graded on 176 cases. §2 is the four-bank read to understand before touching the sampler; §5.2 is the part to read before trusting the cross-check, because angrylion copies eight bytes at a time where parallel-rdp computes each pixel, which makes seven disputes; and §5.3 is the method that found them, which is the part worth copying into the next slice.

[`Mars_RdpTwoCycle.md`](Mars_RdpTwoCycle.md) is Phase D's ninth slice: the two-cycle mode — two combiner and two blender cycles per pixel, the second cycle's texel and the conversion of one texel from another, the two tiles its level of detail picks, and the order in which one pixel's work interleaves with the next's — graded on 159 cases. §1 is the order to read before touching the pixel loop; §5.2 is the part to read before trusting the cross-check, because angrylion pipelines the cycles and parallel-rdp does not, which is all three of the slice's disputes.

[`Mars_RdpLod.md`](Mars_RdpLod.md) is Phase D's eighth slice: the level of detail in the one-cycle mode — how far a pixel's texture coordinates move, the mipmap tile that picks under detail and sharpen, and the fraction the combiner reads — graded on 153 cases. §2 is the measurement to read before touching the pixel loop; §4.2 is the part to read before trusting the cross-check, because parallel-rdp measures this mode the two-cycle way and the random cases are graded against angrylion alone.

[`Mars_RdpFiltering.md`](Mars_RdpFiltering.md) is Phase D's seventh slice: four texels read where filtering or a palette asks for them, the three-point bilinear filter and its mid-texel average, palette lookup, and the palette load — graded on 176 cases. §2 and §4.1 are the parts to read before touching the sampler; §5.2 settles a palette-load disagreement the textures slice left open, which turned out to be the references' starting tile size, and §5.5 records a new case that drew outside its own scissor.

[`Mars_RdpTextures.md`](Mars_RdpTextures.md) is Phase D's sixth slice: the display processor's texture memory, tile and block loads from RDRAM, texture rectangles, perspective division and point sampling in every format — graded on 203 cases, texture memory included. §2 and §3 are the texture-memory layout to read before touching a load; §7 is where the references disagree six times, where parallel-rdp refuses uploads, and where two defects in the test itself were found.

[`Mars_RdpDepth.md`](Mars_RdpDepth.md) is Phase D's fifth slice: shade and depth carried from a triangle's coefficients to each pixel, corrected at partly covered pixels, and the depth buffer's encoding, four compare modes and store — graded on 171 cases. §1.2 is the part to read before touching the walker; §1.3 and §3.2 are two reference rules Mars deliberately omits because nothing can observe them, and §6 includes two decal cases that had never drawn a pixel.

[`Mars_RdpCoverage.md`](Mars_RdpCoverage.md) is Phase D's fourth slice: the one-cycle mode for primitives with no shade, texture or depth — coverage from the walker's sub-scanlines, the combiner, the blender and its hardware divider, dither, and a framebuffer with hidden RDRAM — graded on 177 cases. §6 is the part to read before trusting either reference on this mode: the two disagree on the combined input and on one 8-bit blend, the reference's noise is a validation construct, and the first "disagreements" were the test's own malformed commands.

[`Mars_RdpTriangles.md`](Mars_RdpTriangles.md) is Phase D's third slice: the edge walker that turns a triangle's words into one span per row, drawn in the fill cycle and graded against angrylion on eighty-two triangles. Read §2.1 before touching it — the edges are stepped from the top of the row containing the top vertex, not from the vertex — and §4.3 for the breakages its cases were built to catch.

[`Mars_Video.md`](Mars_Video.md) is Phase E's first slice: the video interface — fourteen registers, the geometry they imply, the borders a frame leaves behind and the walk that scans a frame buffer into the raster — graded on ninety scanned frames. §0 is the harness work that had to come first and the result that shapes the rest: parallel-rdp's own conformance suite says the two references **agree** about this whole device, which Phase D never managed. §2.4 is the state to understand before touching it, §3.1 is a defect that showed up two cases after the one that caused it, and §3.3 is a retired argument worth reading before you claim a rule is unobservable. §2.13 is a defect in the walker's stamped memos that only a counter wrap reaches, and the constructed case that shows it.

[`Mars_VideoFilter.md`](Mars_VideoFilter.md) is Phase E's second slice: the anti-aliasing filter — a pixel's coverage read back out of RDRAM's hidden ninth bits, the six neighbours it is weighed against, and the pull towards the two that bracket it — graded on one hundred and thirty cases. §5 is the part to read first and the reason this page exists in the shape it does: the FPGA core implements this exact filter in a vocabulary entirely its own, so for once its agreement is evidence, and its independent construction proves two things about the software reference that the software reference's own form hides. §2.2 is the rule to keep in mind when reading a filtered picture, §3 is the one thing the referee contradicts, and §4.1 says what a first-run pass is and is not evidence for.

[`Mars_VideoPasses.md`](Mars_VideoPasses.md) is Phase E's third slice: the three passes past the filter — the dither filter that undoes what the display processor dithered, divot's median of three, and gamma — graded on one hundred and fifty-one cases. §3.1 is the part to read first, and the only place in Phase E where the right answer was to build less: the gamma dither reads a noise that angrylion hashes from the pixel's position and the FPGA takes off a free-running shift register, so the two cannot agree and Mars implements neither. §1 proves a clamp both references carry can never fire, and §5 is the referee confirming the pipeline's order from the way its RAM is wired.

[`Mars_VideoTiming.md`](Mars_VideoTiming.md) is Phase E's fourth slice: the half line the signal is on, and the interrupt a game waits for — the first thing in the interface that runs without being asked. §0 is the part to read first, because nothing that graded the three slices before it can grade this one: the dump has no clock, the reference assumes the host keeps the current-line register, and the corpus tests no video group. What grades it instead is a prediction `Mars_Microcode.md` §3 registered before the device existed — delete the stand-in interrupt and a commercial game must still reach its display list — and §3 is that experiment, including why the run fails while both the stand-in and the real device are present.

[`Mars_Serial.md`](Mars_Serial.md) is Phase E's fifth slice: the serial interface and the block the PIF runs for it — sixty-four bytes each way, and the joybus walk that answers a game asking what is plugged in and which buttons are held. §0 is what grades it, and it is three different things: the corpus, which named six PIF RAM groups and gave up exactly six when §1 widened a rule built two slices earlier for a different device; a prediction `Mars_Microcode.md` §3 registered before either device existed, now complete, so that test runs with no stand-ins at all; and thirteen unit tests, because there is no software reference for a PIF. §5 says why the referee is the source here and why that makes its agreement unfalsifiable rather than strong.

[`Mars_Audio.md`](Mars_Audio.md) is Phase E's audio slice: the audio interface's two buffers, its DAC off the video clock, and the queue a frontend drains. §0 is what grades it when the corpus has no audio group — the FPGA core as the source, two emulators read beside it, and two games' recordings as the end-to-end check — and §3.1 and §3.2 are the two places another reading exists.

[`Mars_Save.md`](Mars_Save.md) is Phase E's save slice: the EEPROM on the joybus's fifth channel, SRAM and FlashRAM on the cartridge's second domain, the Controller Pak in the first port, and the files they are kept in. §1 is how a cartridge's chip is named when nothing in the image says — the image's own header, a table, the last save's length, and then the game's first move — and §6 is the table, which holds only the one chip a game's behaviour cannot reveal. [`Mars_SaveStates.md`](Mars_SaveStates.md) is Phase F's first slice: the whole machine in a 6.4MB state, the three things reflection cannot walk, and the replay that grades it — each game saved, loaded into a fresh core, and run beside the original. §4 is also where the evidence says what it cannot see: a field wrongly left out of the state that no replayed frame depends on.

[`Mars_Debug.md`](Mars_Debug.md) is Phase F's debugger: breakpoints before each instruction, stepping over and out of MIPS calls, watches and data breakpoints on processor stores, coverage for both processors, a virtual CPU memory space that reaches memories and never registers, and the RSP listed but not haltable. §7 is what it costs, and why the shared breakpoint registry grew a `CouldBreak` to make that nothing.

[`Mars_Corpus.md`](Mars_Corpus.md) is the hardware corpus as a running instrument rather than as a protocol. **The run now completes** and the corpus reports its own verdict — §1. Read §2 before quoting any "every X test passes" claim from another page here: a run that stops early reports on the part of the world it reached, two claims had to be qualified because of it, and one of them was this page's own. §3 is the census of the complete run, in which no group testing the CPU or the RSP as a processor still fails; §9 and §10 are the two slices that cleared them. §8 is why no earlier run could: the corpus needs an Expansion Pak, and the harness had been running it on a 4MB machine.

[`Mars_Disassembler.md`](Mars_Disassembler.md) is not a slice: it is the two pure decoders a debugger listing needs, one for the VR4300 and one for the RSP, which name exactly what Mars's interpreters execute and print everything else as `.word`. §3.1 is the part to read first — the six groups of encodings the interpreters execute without a name, one of which is an RSP interpreter behaviour `Mars_Rsp.md` §6 says should not exist. §6 is the VR4300's grading, two hundred thousand encodings against capstone with every disagreement classified and none of them Mars's; §7 is the RSP's, which has no such oracle and is read against the corpus's own assembler and four implementations instead.

The remaining per-component pages (the video, audio and serial interfaces, and the rest) get added here as the phases that build those subsystems land, the same way `Venus - SNES/`'s and `Mercury - GB-GBC/`'s were.

See `Man pages/EmuSen_Core_Naming_Scheme.md` for the full core naming scheme, and `Man pages/Hardware/README.md` for how this documentation set is organized.

# EmuSen Frontend Driver (`EmuSen.Hotaru/Program.cs`, `App.axaml.cs`, `Views/GameWindow.axaml.cs`)

Covers Hotaru's launch sequence and its actual emulator driver: ROM selection, log setup, wiring the debug toolchain together, the emulation thread's per-frame loop, and every F-key/dev hotkey. Same reorganization as `Man pages/Hardware/` and `EmuSen_Settings_Reference.md`: long inline comments move here, code keeps only short local pointers back to this doc.

Not hardware-specific (that's `Man pages/Hardware/`) and not configuration (`EmuSen_Settings_Reference.md`) — this is the thing that actually drives the emulator frame by frame, so it gets its own page directly under `Man pages/`.

Lives in its own project, `EmuSen.Hotaru/`, not inside `EmuSen.csproj` — that split happened once `EmuSen.csproj` stopped being allowed to have a `Main`/window of its own at all: the Avalonia frontend (`EmuSen.Mistress9/`, renamed from `EmuSen.Frontend/`) used to inherit this project's `Main`/window-ownership just by referencing `EmuSen.csproj` to reach the emulation core, which is backwards (one frontend depending on the other's frontend-specific baggage). `EmuSen.csproj` is a pure library now; `EmuSen.Hotaru` and `EmuSen.Mistress9` are true siblings, each independently referencing it (and `EmuSen.Serenity`) — see `EmuSen_Project_Overview_v2.md` §1/§2.

**This revision: the DianaOS terminal is "always live" now - no F4 mode-switch needed to type a command.** From the moment a ROM loads, `GameWindow` runs a dedicated `_consoleReaderThread` (`ConsoleReaderLoop`, started in the constructor) that owns `ConsoleLineReader.ReadLine` for the window's whole life, not just while F4/a breakpoint has the emulation thread blocked in `RunDebugPrompt`. While the game is running normally, a typed line is classified via `DianaOSInterpreter.TryGetReadOnlyFastPath` (a pure, parse-only check - see `EmuSen/DianaOS/DianaOSInterpreter.cs`'s own comment on it): a single, complete, bare command whose registered `IDianaOSCommand` reports `IsReadOnly` (`mem`, `regs`, `coretop`, ...) answers immediately, right there on the reader thread, without the emulation thread ever noticing - the same "a read-only view of live core state, unsynchronized, is an accepted race" precedent `CoretopWindow`'s own polling already relies on. Anything else (a mutating command, a pipe/`&&`/control-flow line, an unresolved command) is queued (`_pendingCommandQueue`) and drained once per frame by the new `ProcessPendingConsoleCommands`, called from `EmulationLoop` right alongside `ProcessHotkeys` - so it runs inline on the emulation thread's own next tick, the same "queue it on one thread, drain it once per frame on another" shape this file's `_request*` hotkey flags already established, just generalized to an unbounded stream of typed lines. **F4/breakpoint halts are unchanged** - `RunDebugPrompt` still fully blocks `RunFrame()` exactly as before, it just now receives its lines from `_consoleReaderThread` via a `_haltedLineQueue` handoff instead of reading the console itself (the reader thread is the sole owner of `ConsoleLineReader.ReadLine` now, so it can't also be called directly from the emulation thread). `_interpreterLock` (a plain `lock`, held only for one command's `Execute`, never across a blocking console read) serializes the two things that can now call `_debugCmd.Submit` - the reader thread's fast path, and whichever thread is executing a queued/halted line for real - since a single `DianaOSInterpreter` has real mutable state beyond core reads (variables, history, `$?`) that isn't safe to enter from two threads at once. Command classification itself (`IDianaOSCommand.IsReadOnly`) is a new interface property every command states explicitly; a command with mixed read/write sub-verbs (`watch`, `bp`, `framelog`, `cheat`, `snapshot`, `search`, `history`, `log`, `trace`) reports `false` conservatively, since the property can't vary per invocation - and `coretop`'s raw-terminal mode (which blocks indefinitely on its own `Console.ReadKey` loop until Ctrl+C) also reports `false` despite never mutating core state, specifically so an open dashboard can't hold `_interpreterLock` open-ended and stall the frame-tick drain. Multi-line constructs (`for`/`while`/`if` spanning several lines) stay F4/breakpoint-halt or single-line `source` only - the live terminal doesn't attempt to collect continuation lines across frames.

Previous revision: `core <name> <path>` can swap the running ROM now, from inside an already-open GameWindow. Hotaru had NO way to change ROMs mid-session before this - the only `core` handling that ever existed was `RunStandaloneShell`'s own pre-window one (§3, below), which only runs once, before `VenusCore` exists at all. `EmuSen.DianaOS.Commands.CoreCommand` (registered in `debugCmd`'s own `extraCommands`, alongside `CoretopCommand`/`StateCommand` - see §1) validates a `core`/`path` pair exactly like `TryResolveCoreCommand` always has, then signals `HostAction.LoadCore` instead of returning a plain string - `GameWindow.SwapCore` reacts by reloading `VenusCore` in place (`LoadRom` is a re-initializer, not a constructor-only step) and rebuilding `_debugTarget`/`_debugCmd`/`_frameRecorder` from the fresh `Cpu`/`Bus`/`Renderer` those produce, the same "fresh `SnesDebugTarget` per load" discipline `EmuSen.Mistress9`'s own `MainWindow.LoadRom` already established (watches/breakpoints/cheats registered against the old ROM don't survive a swap, on purpose, matching that same precedent). Refuses to swap while a frame recording is active rather than silently orphaning it. This is part of a broader pass making DianaOS's own command registry the actual source of truth for "everything you can do" instead of "everything except a few special-cased things" - `resume`/`shutdown`/`step`/`state save|load` went through the same promotion in earlier phases of that same pass; see each command's own entry in `EmuSen_Debugging_Tools_Reference_v5.md` and `HostAction`'s own comment (`EmuSen/DianaOS/HostAction.cs`) for the mechanism this all runs on.

Earlier revision: Hotaru moved off Raylib entirely, onto Avalonia. Window, rendering, shaders, audio, and input were all Raylib before; all four are now Avalonia/SkiaSharp/SDL, matching (and in the audio/gamepad case, directly duplicating) `EmuSen.Mistress9`'s own stack. The console-first launch experience (`RunStandaloneShell`, §3 below) is completely unchanged — no window of any kind opens until a ROM actually resolves. What changed is everything from that point on: `Program.cs`'s `Main` now hands off to `App.axaml.cs`/`Views/GameWindow.axaml.cs` (§1) instead of driving a Raylib game loop itself; the on-window Raylib debug overlay (VRAM sheet/CGRAM swatch/register text drawn directly onto the game window, the old `O`/`GraphicsSettings.ShowDebugPanels` panels) is gone entirely — DianaOS's `regs`/`sprites`/`pal`/`tile`/`vramsheet`/`paletteswatch` commands and the `coretop` dashboard already covered the same data, and `EmuSen.Mistress9` (always headless in this sense) never had it either; and `EmuSen.Serenity`'s `FramePresenter`/`GameFrameControl` are now a real Avalonia-native, Skia-backed presenter with actual shader support (`ShaderEffect.Scanlines`/`Crt`, ported to SkSL — see §2's F8 entry), not deferred or dropped along with Raylib. See `EmuSen_Project_Overview_v2.md` for the updated project tree and `EmuSen_Core_Gameplan.md` for why this was worth doing (it also finally answers `EmuSen.Mistress9`'s own long-standing "GPU-capable rendering surface" TODO, even though Mistress9 itself hasn't adopted the new presenter yet).

## 1. `Main`/`App`/`GameWindow` — startup sequence

1. **ROM path resolution — DianaOS is now the only thing shown at launch, always.** `Main` always calls `RunStandaloneShell(...)` first and returns immediately if it comes back `null` — no ROM, no core, no window of any kind (Avalonia or otherwise) until a ROM path is actually resolved (§3, below). This isn't gated on "no CLI arg": a ROM path given on the command line (`dotnet run -- /path/to/game.smc`) is passed into `RunStandaloneShell` as a starting path, treated purely as a shortcut for typing `core <name> <path>` at the prompt yourself, not a separate way to skip the shell. A valid file resolves and returns immediately (straight to gameplay, no interactive loop needed); an invalid one prints why and falls through into the same interactive prompt a bare launch gets, so a typo'd CLI arg lands you at a usable shell instead of a dead process. Avalonia (like Raylib before it) has no built-in file picker in this frontend, so `core`/a CLI arg is the standard way to pick a ROM here — `EmuSen.Mistress9` has a real "Open ROM..." dialog (plus a "Browse ROMs..." list and a configurable default directory) instead, for anyone who prefers that.
2. **`VenusCore` construction.** This is the actual emulation driver — CPU/PPU/APU/memory, the per-scanline timing loop, save states, SRAM — not `Main` itself. See `Cores/ICore.cs`.
3. **Log directory setup — deliberately placed here, not earlier.** `Logs/<CoreName>/console_<timestamp>/` needs `core.CoreName`, which only exists after `VenusCore` is constructed. This means the one console line printed before this point ("ROM Loading: ...") only reaches the terminal, not the file — an accepted, minor loss — and a ROM-not-found early exit never creates an empty log folder at all, since it returns before `VenusCore` (and therefore the log dir) exists.
4. **Debug toolchain wiring.** `SnesDebugTarget` and `DianaOSInterpreter` are built once here, so both the F1 hotkey and the F4 interactive prompt go through the *same* underlying data rather than each reaching into `cpu`/`bus`/`ppu` independently.
5. **Power-on watch registration (Yoshi/coin investigation).** Two `WatchRegistry` entries — `WRAM 0x8000` (0x1800 bytes, the graphics-upload staging buffer) and `WRAM 0x0D80` (0x80 bytes, the job-table region near the DMA dispatcher) — are registered here instead of via the F4 prompt, specifically so they're active from the very first CPU instruction rather than from whenever a human gets around to pressing F4 (hundreds of frames in).
6. **Handoff to Avalonia.** Everything from here on lives in `App.axaml.cs`/`Views/GameWindow.axaml.cs`, not `Main`. `Main` calls `AppBuilder.Configure(() => new App(core, debugTarget, debugCmd, frameRecorder, statePath))` — the generic `Configure<TApp>(Func<TApp>)` overload, type-inferred from the lambda — rather than the usual parameterless `Configure<App>()`, specifically so the state `Main` already built above threads straight into `App`'s constructor instead of being reconstructed inside `OnFrameworkInitializationCompleted`. `.UsePlatformDetect().WithInterFont().LogToTrace()` plus the same Linux-only `.UseWayland()` opt-in `EmuSen.Mistress9`'s own `Program.cs` uses (Avalonia 12.1's native Wayland backend isn't picked up by `UsePlatformDetect()` on its own yet). `StartWithClassicDesktopLifetime(args)` blocks `Main` until the window closes; `App.OnFrameworkInitializationCompleted` constructs one `GameWindow` (no menu/chrome — "just the game," matching the old Raylib build's own simplicity) and that's the entire window this frontend ever opens for gameplay itself (`coretop -w`/`feed -w` open separate windows on demand — §3a).
7. **The emulation thread (`GameWindow.EmulationLoop`).** Started from `GameWindow`'s constructor, entirely separate from the Avalonia UI thread. Owns `core.RunFrame()`, audio (`Audio/AudioPlayer.cs`, SDL-backed), the per-frame hotkey dispatch (§2, below), the per-frame drain of queued live-terminal commands (`ProcessPendingConsoleCommands`, below), and — the one genuinely load-bearing design choice here — **the blocking F4 DianaOS console prompt itself**. Because the prompt and the frame loop share this one thread by construction, F4 still blocks gameplay exactly like it did in the Raylib build, and no `pause`/`resume` mechanism is needed the way `EmuSen.Mistress9`'s console window needs one (that window's console runs concurrently with its own separate emulation thread — a different shape). One real, positive side effect falls out of this for free: because the *window* (paint/input pump) lives on the UI thread, independent of whichever thread the console prompt blocks, **the game window stays movable/resizable/closable while F4 is open** — unlike the old Raylib build, where the window and the prompt shared one thread and froze together. Each iteration: `core.RunFrame()` → (breakpoint-halt check, same as before) → `_audioPlayer.Pump(core)` → hand the frame off to `GameFrame` (this window's `GameFrameControl`, from `EmuSen.Serenity`) via the same coalescing `Interlocked.Exchange`/`CompareExchange` present pattern `EmuSen.Mistress9`'s own `MainWindow.SubmitFrame` uses — only one `Dispatcher.UIThread.Post` is ever in flight, so a slow UI thread drops intermediate frames instead of backing up a queue — then the per-frame hotkey dispatch (§2), then the per-frame console-command drain (see this page's own top note on the "always live" terminal).
7a. **A fourth, dedicated console-reader thread (`GameWindow.ConsoleReaderLoop`)**, started alongside the emulation thread in the constructor, is the sole owner of console input for the window's whole life - see this page's own top note for the full "always live" design. It never blocks the emulation thread on a console read; the only thing it shares with that thread is `_interpreterLock`, held briefly around each `DianaOSInterpreter.Submit` call.
8. **Keyboard/gamepad input.** Applied the moment it changes, not polled once per frame the way Raylib's `InputBindings.ApplyInput` was: `GameWindow`'s own `KeyDown`/`KeyUp` handlers (via `Input/HotaruKeyMap.cs`, the Avalonia-`Key` port of the old `InputBindings.cs` keyboard scheme — that file is deleted) and a 60Hz gamepad-poll `DispatcherTimer` (via `Input/GamepadManager.cs`/`GamepadBindingMap.cs`, duplicated from `EmuSen.Mistress9`'s own SDL-backed copies) both write straight into `core.Bus.Input` — combined with OR logic, same "either device works, no need to pick one" convention the console build always had. This is the same event-driven pattern `EmuSen.Mistress9`'s `MainWindow` already established; the console build's own poll-every-frame model only ever existed because Raylib has no push/event API for continuous key state.
9. **Shutdown.** `GameWindow`'s `Closing` handler — not `Main` — runs `core.SaveSram()` (final flush beyond the periodic autosave already inside `RunFrame()`) and disposes the gamepad/audio devices; `Main` itself just waits for `StartWithClassicDesktopLifetime` to return. `Main`'s own `AppDomain.ProcessExit`/`UnhandledException`/`SIGTERM`/`SIGINT` handlers (unchanged from the Raylib build) still separately flush `CategorizedLogWriter`'s buffered log queue on every OS-level exit path, since that's a process-lifetime concern, not a window-lifetime one.
10. **Top-level `catch`.** Any unhandled exception on the emulation thread prints `[CPU HALT] <message>` and closes the window — the CPU's own `NotImplementedException` for an unimplemented opcode is the most common thing this actually catches in practice.

## 2. `GameWindow`'s hotkey dispatch — why request flags, not direct polling

Everything triggered by a keypress (or a bounded background trace) is consumed once per completed frame inside `EmulationLoop` (§1 step 7), the same cadence the old Raylib build's `RunHotkeys` ran at — but the *mechanism* changed along with the threading model: `KeyDown`'s handler (UI thread) can't safely touch `core`/`bus`/`renderer` state directly while the emulation thread might be mid-`RunFrame()`, so it just sets a `volatile bool` request flag (edge-detected against a physical-key-held set, so an OS key-repeat doesn't re-trigger it), and `EmulationLoop` reads-and-clears each flag once per iteration. Exactly one writer (`KeyDown`) and one reader/clearer (`EmulationLoop`) per flag — the same single-writer/single-reader race `EmuSen.Mistress9`'s own `ApplyButtonState` already accepts for continuous button state, just applied to one-shot hotkeys too. The one exception is **F8** (shader cycling), which touches nothing but `GameFrame.ActiveEffect` (a UI-side property with no core state involved at all), so it runs directly from `KeyDown` for the most immediate possible feedback.

### Hotkeys

| Key | Does |
|---|---|
| *(every frame)* | `frameRecorder.CaptureFrame(...)` — cheap no-op when not recording; has to run unconditionally (not gated on a keypress) so every frame during an active F6 recording gets captured, not just the frame F6 happened to be pressed on. |
| **F6** | Toggle continuous frame recording — see `Debug/FrameRecorder.cs` and `EmuSen_Debugging_Tools_Reference_v5.md` §3.8. |
| **P** | Starts a bounded 300-frame BG scroll trace (`DebugTools.BoundedTrace`), turning on `AllScrollWriteLogging` for exactly that span and back off automatically when it ends — built for the historical BG2 parallax-jitter investigation (see `Venus_PPU.md` §2), left in as a reusable pattern for the next scroll-timing question. |
| **F1** | Full CPU+PPU state snapshot via `debugTarget.GetSummaryText()` (→ `StateDump.DumpAll`). Formatted to be directly comparable to MesenCE's own Status panel, since that's exactly what used to get hand-transcribed from screenshots during the scroll-jitter investigation. |
| **F2** | Dumps every active OAM sprite's exact X/Y/tile/attribute bytes via `renderer.DumpActiveOam` directly (not through the debug toolchain) — the `sprites` command (F4) is the generalized, toolchain-routed equivalent of just this dump's printed output. |
| **O** | Full backdrop/window/OAM debug dump via `renderer.DumpBackdropAndWindowDebugInfo` — pure `Console` logging with no render-target dependency, same as every other hotkey. This is unrelated to (and survived the removal of) the old on-window Raylib debug overlay — that was pixels drawn onto the game window itself; this has always just been text. |
| **F8** | Cycles the post-processing shader pass — `None -> Scanlines -> Crt -> None` (`FramePresenter.NextEffect(ShaderEffect)`/`GameFrame.ActiveEffect`, `EmuSen.Serenity/Shaders/BuiltInShaders.cs`). Manual A/B toggle for the shader pipeline seam, ahead of any real settings UI or multi-pass preset format. Now a single Skia `SKRuntimeEffect` SkSL shader pass applied to the already-upscaled game image via `GameFrameControl`'s `ICustomDrawOperation` (see `EmuSen_Project_Overview_v2.md`'s `EmuSen.Serenity` entry) — a faithful port of the old GLSL math (same darken-odd-rows factors, 0.78/0.72, and radial vignette), not a redesign. The on-window debug overlay this used to draw *after* (so VRAM/CGRAM/text panels stayed crisp regardless of the active effect) no longer exists at all, so there's nothing left to layer on top of the shaded image. |
| **F7** | Toggles a per-`GameWindow` `_mirrorPlayer1ToPlayer2` flag (off by default, replacing the old static `InputBindings.MirrorPlayer1ToPlayer2`) — also sends every button press to Controller 2, for games that read Controller 2 instead of Controller 1. Super Mario All-Stars' classic sub-games (SMB1/2/3, unlike native SMW) are the known real-world case — confirmed via `EmuSen.Pharaoh90`'s `--tap2`, see `EmuSen_Games_Tested.md`. Leave off for real two-player sessions; forcing it on unconditionally would feed Controller 2 the same input as Controller 1 even with a genuine second pad plugged in. |
| **F4** | Interactive debug command prompt (`GameWindow.RunDebugPrompt`) — see `EmuSen_Debugging_Tools_Reference_v5.md` §3. Blocking by design, on the emulation thread specifically (§1 step 7) — there's no way to pause emulation mid-frame, so this just blocks that thread for as long as it takes to type commands, while the window itself stays responsive. `help` for the command list, `resume`/`continue`/`c`/an empty line to resume the game, `shutdown`/`quit` to actually terminate the process (§3, below). Note this is now the **fully-blocking, classic** prompt specifically - as of this page's top note, DianaOS also answers a great deal without F4 at all, from the `DianaOS $` prompt that's live continuously; F4 is still the right tool for a real "stop everything and step through this" session, or for a multi-line construct the live terminal doesn't handle. |
| **F3** | Saves the current frame as a real PNG (via `Imaging/FrameImageWriter.SavePng`, SkiaSharp's `SKImage.Encode` directly — not Avalonia's `WriteableBitmap.Save`, and not Raylib's `TakeScreenshot`) plus a companion `.txt` (core name, frame number, wall-clock) under `Logs/<CoreName>/` — see `EmuSen_Debugging_Tools_Reference_v5.md` §3.6. Captures the **raw pre-shader frame** (`core.GetFrameBufferRgba()`) rather than the composited, possibly-shaded window — a deliberate, accepted behavior change from the Raylib build (which captured the actual window surface): the alternative would need a UI-thread round trip from this method's own emulation-thread call site every single recorded frame, for a feature (matching whatever F8 shader happens to be active) not worth that cost. |
| **F5 / F9** | Save/load state, one slot per ROM (named to match its `.srm`). Both go straight through `VenusCore.SaveState`/`LoadState` (via `ICore`). The same operation is also reachable as a real DianaOS command from the F4 prompt now - `state save\|load [path]` (`EmuSen.DianaOS.Commands.StateCommand`, shared with `EmuSen.Mistress9`'s own console) - see `EmuSen_Debugging_Tools_Reference_v5.md`'s `state` entry. |

**Periodic SRAM autosave is not here** — it lives inside `VenusCore.RunFrame()` itself, not duplicated in the frontend.

**The always-on `[STATUS]` heartbeat and the per-second `[FPS]`/phase-breakdown diagnostic block are gone** — both used to print unconditionally, every 60 frames and every ~1 second respectively, regardless of whether anyone was watching the console. Now that DianaOS is Hotaru's primary UI (§1, above) rather than an occasional F4 detour, that kind of automatic console spam competes with the shell for the same terminal instead of being a harmless aside — inspection is fully on-demand now: `coretop` (`EmuSen_Debugging_Tools_Reference_v5.md` §3.17) covers the live hardware-load/fps-shaped questions the old `[FPS]` block answered, and F1/`regs`/`sprites`/the other hotkeys and DianaOS commands above cover everything `[STATUS]` used to print. Nothing about `VenusCore.RunFrame()`'s own per-subsystem timing counters (`LastFrameCpuSpc700Ms`/`LastFramePpuMs`/etc.) was removed — only this frontend's unconditional printing of them; `coretop`'s hardware-load bars still read them live via `SnesDebugTarget`'s `frameTimings` delegate.

## 3. `RunStandaloneShell` — Hotaru's launch screen, ROM arg or not

Every launch goes through this now, not just a bare `dotnet run` - `Main` always calls `RunStandaloneShell(initialRomPath)` first and returns before any of §1's `VenusCore`/log/window/audio setup runs. No core, no `SnesDebugTarget`, no window of any kind - just `DianaOSInterpreter.CreateDefault(null)` and a plain read-eval-print loop reusing `ConsoleLineReader` (the same Up/Down-history-aware line reader the F4 prompt uses) for input, printed and ready before anything else in this frontend does a single thing.

`initialRomPath` is whatever came in as `args[0]`, or `null` for a bare launch. Given a path, `RunStandaloneShell` checks it immediately: a real file prints `[ROM] Loading: ...` and returns it right away, skipping the interactive loop entirely and going straight into §1's gameplay setup, same destination `core <name> <path>` reaches (below) - a CLI arg is just a faster way to say the same thing, not a separate way to bypass the shell. A path that doesn't exist prints `[ERROR] ROM not found: ...` and falls through into the ordinary interactive loop instead of exiting, so a typo'd argument still lands you somewhere useful (`core` a different path, or `shutdown`) rather than a dead process.

Deliberately its own small method rather than calling `RunDebugPrompt` with a null core: `'step'` (`EmuSen.DianaOS.Commands.StepCommand`, registered globally now - see below) fails cleanly with "No ROM loaded" here rather than doing anything useful, the `state save|load` command is registered only in the in-game `debugCmd` (see `EmuSen_Debugging_Tools_Reference_v5.md`'s `state` entry) so it's genuinely unreachable here at all, and `RunDebugPrompt`'s whole "resume the game" framing (an empty line means resume there) doesn't mean anything without a game running - threading null-core checks through every one of those cases would make the actually-in-a-game path harder to follow for no real benefit. `RunStandaloneShell`'s own way out is `'shutdown'`/`'quit'` (`EmuSen.DianaOS.Commands.ShutdownCommand` - see below) or EOF (`ConsoleLineReader.ReadLine` returning `null`, e.g. Ctrl-D) - there's no `'resume'` here at all (nothing to resume), and an empty line does nothing, matching a real shell's own behavior rather than acting as another way to exit.

**`resume`/`shutdown`/`step` are real, shared DianaOS commands now** (`EmuSen.DianaOS.Commands.ResumeCommand`/`ShutdownCommand`/`StepCommand`, registered in `DianaOSInterpreter.CreateDefault`'s own standard list - see `EmuSen_Debugging_Tools_Reference_v5.md`'s entries for each), not hand-rolled string matches inside `RunDebugPrompt`/`RunStandaloneShell` anymore. Each signals a `HostAction` (`EmuSen.DianaOS.HostAction.Resume`/`Shutdown`/`Step`) - `DianaOSResult`'s own escape hatch for a command that needs to change the *calling* frontend's own control flow (break `RunDebugPrompt`'s loop, or `RunStandaloneShell`'s), which a plain string result could never express. `'continue'`/`'c'` and `'quit'` and `'s'` are recognized as plain aliases inside `DianaOSInterpreter.Dispatch` itself (normalized to the canonical name before the registry lookup, the same way `'source'`/`'.'` already work), not separate registry entries - `help` only ever shows each command's line once.

**`'shutdown'` means the same thing in both places now** - typing it at the F4 prompt mid-game actually terminates the whole process (`RunDebugPrompt` returns `true`, which `ProcessHotkeys` and `EmulationLoop` both propagate up to `RequestClose()` - setting `_running = false` and posting `Close()` onto the UI thread, so the window closes and its own `Closing` handler runs the same `core.SaveSram()`/audio-and-gamepad-disposal sequence a normal window close takes), and typing it here does the same thing more directly (this loop has no game/window/audio to tear down first). This replaced an old, genuinely confusing overload of the word `'exit'`: it used to mean "resume the game" inside `RunDebugPrompt` but "quit the process" inside `RunStandaloneShell` - the same word, two unrelated actions depending on which of these two methods happened to be running. `'resume'` (new, alongside the pre-existing `'continue'`/`'c'`/empty-line synonyms) and `'shutdown'` (renamed from `'exit'`, alongside the pre-existing `'quit'` synonym) now each mean exactly one thing, everywhere.

Every general-purpose DianaOS command (`echo`/`sed`/`grep`/`awk`/`ls`/`cd`/`nano`/`source`/`if`/`for`/`while`/`test`/...) works exactly the same with no target as it would mid-game - only commands needing real hardware access (`mem`/`regs`/`watch`/...) report a clean `"No ROM loaded"` via their own `RequireTarget` guard (`EmuSen_Debugging_Tools_Reference_v5.md` §3.3) instead of a crash. In practice this makes a bare `dotnet run --project EmuSen.Hotaru` (no ROM argument) a quick way to poke around the shell itself - run a `source`d script, `nano` one up first, check `awk`/`sed` behavior, browse `man` pages - without needing a ROM on disk at all.

**`core <corename> <path>` here - the FIRST way to reach a game, before any window exists.** Still not a `DianaOSInterpreter` command in this shell specifically (same reasoning as `'shutdown'`/`'resume'` used to have before those two were promoted, above - at this point it needs to hand a validated ROM path back to `Main`, which a command's own `DianaOSResult`/`HostAction` contract has no way to do before `VenusCore` even exists yet to attach a `HostAction.LoadCore` handler to); parsed as a plain string by `RunStandaloneShell` itself, then validated by a small private helper (`TryResolveCoreCommand`) before `RunStandaloneShell` returns the resulting path and `Main` proceeds into the exact same `VenusCore`/window/audio setup (§1) a CLI-arg launch already goes through - `core` doesn't duplicate any of that, it just supplies the path a different way. `EmuSen.DianaOS.Commands.CoreCommand` (§1's own revision note, above) is the *other* `core` - reachable once a window's already open, for swapping ROMs mid-session, something this pre-window path was never trying to do at all. The two share `CoreDescriptor` (display name + supported file extensions, promoted into `EmuSen.DianaOS.Commands` since it's genuinely core-agnostic, the same reasoning `IDebugTarget` itself stays agnostic) but keep separate registry instances and separate validation call sites on purpose - unifying them would mean threading a `HostAction`-shaped result back through a code path that runs before there's anything to hand that action to. Only one entry exists in Hotaru's own registry today (`"venus"`/`"snes"`, both aliasing the same `SNES (Venus)` descriptor, extensions `.smc`/`.sfc`) because only one core is actually implemented - the registry exists so a future second core has an obvious place to register itself, not because multiple cores work today.

`core` validates, in order, and reports a clean, specific error for each without touching anything real: malformed usage (not exactly 3 words), an unregistered core name (lists what IS supported), a ROM path that doesn't exist, and - the actual point of the extension check - a ROM whose extension isn't one the named core's `CoreDescriptor` lists (`core venus game.nes` → `"'.nes' is not a supported ROM type for SNES (Venus) - expected: .smc, .sfc"`). That last check exists because `Cartridge` (`Cores/Nintendo/Venus - SNES/Memory/Cartridge.cs`) has no ROM-format validation of its own at all - it unconditionally treats whatever bytes it's given as SNES-shaped (its only special-casing is copier-header stripping, based on file length alone) - so handing it a ROM for a different system entirely would previously have just silently produced garbage emulation instead of a clear error at the point the mistake was actually made.

## 3a. `DebugWindows` — `coretop -w`'s window, now that Avalonia is the primary app

`coretop` (`EmuSen_Debugging_Tools_Reference_v5.md` §3.17) is a raw-terminal dashboard that necessarily blocks the console for as long as it runs — fine for inspecting a paused moment, useless for watching hardware state live *while playing*, since typing at the same terminal the game is asking for input from was never possible to begin with. `coretop -w` opens the same dashboard as a separate window instead.

Before this migration, that needed a whole second Avalonia dispatcher bootstrapped on its own dedicated thread (`AvaloniaHost.cs`, deleted — see git history), specifically because Raylib supported exactly one native OS window per process and owned the actual main thread. Now that Avalonia *is* Hotaru's primary application (§1, above) with its own dispatcher already pumping as part of the normal Avalonia app lifecycle, opening a second window is just... opening a second window — `Views/DebugWindows.cs` (new, replacing `AvaloniaHost.cs`) is a small static class with no thread-bootstrap logic left in it at all:

- `ShowCoretopWindow(IDebugTarget)` just does `Dispatcher.UIThread.Post(() => { ...create-or-reuse a single cached CoretopWindow... })` — no `EnsureStarted()`, no `ManualResetEventSlim` wait, since `Dispatcher.UIThread` is already alive by the time this can ever be called (both entry points are only reachable via commands typed at the F4 prompt, which only exists after `GameWindow`'s constructor — and therefore `OnFrameworkInitializationCompleted` — has already run). Same at-most-one/reuse pattern the old `AvaloniaHost` had, and the same one `EmuSen.Mistress9`'s own windowed `coretop` already established.
- `Views/CoretopWindow.axaml(.cs)` itself is unchanged — it was always a plain Avalonia `Window` polling `IDebugTarget` on a `DispatcherTimer`, with no dependency on how it got shown. Still a deliberate near-duplicate of Mistress9's own `CoretopWindow` (same layout, same 250ms refresh, same `ProgressBar`/`WriteableBitmap` rendering) rather than a shared class, matching this project's established precedent that Hotaru and Mistress9 stay separate, non-sharing UI projects.

Wired into `Main`'s in-game `debugCmd` via the same `extraCommands` override-by-name mechanism Mistress9's own windowed `coretop` uses: `DianaOSInterpreter.CreateDefault(debugTarget, new IDianaOSCommand[] { new CoretopCommand(DebugWindows.ShowCoretopWindow) })` replaces the standard registry's plain, opener-less `coretop`. `RunStandaloneShell`'s own `CreateDefault(null)` call (§3, above) is deliberately left unwired — there's no ROM loaded there, so `-w` would always fail on "No ROM loaded" before ever reaching the window-opening logic, and wiring it up would add nothing reachable.

**Closing the window is `-w`'s Ctrl+C.** There's no separate raw-terminal loop running alongside it to keep in sync — choosing `-w` means the terminal dashboard never starts for that invocation at all — so the window's own `Closed` event (which stops its refresh timer) is the entire "stop watching coretop" action, exactly the one decision Ctrl+C makes in the terminal version.

**Accepted risk, stated plainly:** `CoretopWindow`'s refresh timer calls `IDebugTarget` methods (`GetHardwareLoad`, `GetCpuRegisters`, ...) on the UI thread while `GameWindow`'s own emulation thread concurrently calls `core.RunFrame()`, with no synchronization between the two — the same class of narrow data race that originally motivated `EmuSen.Mistress9`'s `pause`/`resume` commands. This frontend has no pause mechanism of any kind to close that gap with, so it's accepted for now as a read-mostly debug view, not something that ever feeds back into gameplay logic. Not verified visually in this environment — no display server was available to confirm the window actually renders/behaves as designed on either frontend; the headless-testable parts (`-w` parsing, the opener-invocation, the no-opener fallback) are covered instead by `DianaOS/CoretopWindowFlagTests.cs`.

## 3b. `feed`/`feed -w` — watching gameplay without needing the game window

Reachable only from the F4 debug prompt (`GameWindow.RunDebugPrompt`, §3's own reasoning for why `resume`/`shutdown`/`step`/`state` live there rather than as registered commands applies here too — `feed` needs to hand control back to the emulation thread's own loop, which a plain `IDianaOSCommand` can't do). Typed alone, it does exactly what `resume` does — breaks out of the prompt loop so `EmulationLoop` starts calling `core.RunFrame()` again — but also arms a second way back into the prompt that doesn't depend on the game window having keyboard focus at all: pressing Ctrl+C at the *terminal* reopens it.

That's implemented as a per-frame poll, not a blocking read — `ProcessHotkeys` (§2) checks `Console.KeyAvailable` once per frame (the same non-blocking technique `coretop`'s own dashboard uses to watch for Ctrl+C, just spread across frames instead of one dedicated blocking loop, since gameplay has to keep running underneath this one) and calls `RunDebugPrompt` again the moment a Ctrl+C key event shows up. `ArmFeedWatch()`/`DisarmFeedWatch()` (`Views/GameWindow.axaml.cs`) own the state this needs: `Console.TreatControlCAsInput = true` while armed (so Ctrl+C arrives as a readable key instead of the process-terminating signal `Main`'s own `PosixSignalRegistration` handlers treat it as normally), and `_feedWatchActive` gating the poll so it's a no-op the rest of the time. `RunDebugPrompt` calls `DisarmFeedWatch()` unconditionally the instant it's entered — by any path, F4 or `feed`'s own Ctrl+C — so a plain Ctrl+C means "shut down" again everywhere else in this frontend the moment you're back at a prompt, exactly like before `feed` existed.

`feed -w` does everything bare `feed` does, plus opens `Views/FeedWindow.axaml(.cs)` via `DebugWindows.ShowFeedWindow(Func<(byte[] Rgba, int Width, int Height)>)` (§3a) — just a `Dispatcher.UIThread.Post` now, the same as `coretop -w`, with no second dispatcher thread to reuse or start. Unlike `CoretopWindow`, `FeedWindow` mirrors the actual game picture (`core.GetFrameBufferRgba()`/`ScreenWidth`/`ScreenHeight`, passed in as a plain delegate so neither `DebugWindows` nor `FeedWindow` need to know anything about `ICore`/`VenusCore` concretely) rather than hardware/debug data, refreshed at ~30Hz — fast enough to read as "watching the game," not a slowly-updating stat readout — into one `WriteableBitmap` reused for the whole session rather than rebuilt every tick, since the screen resolution is fixed once a ROM is loaded. Same accepted data race as `CoretopWindow` (§3a's own paragraph on this) — the timer reads `ICore` state off the UI thread with no synchronization against the emulation thread's own concurrent `RunFrame()` calls, accepted for the same reason: a read-mostly view, never feeding back into gameplay.

`EmuSen.Mistress9` gets its own registered `feed` command (`FeedCommand`, `Views/EmulationControlCommands.cs`) for the same "one word means the same thing everywhere DianaOS runs" reason `coretop` is available on both frontends — but there's no separate window to open there at all: `MainWindow`'s own `GameView` already shows the live picture continuously in the same window the entire time `DianaOSConsoleWindow` is open (they're just two independent Avalonia windows), so `feed` there is just `Activate()` on `MainWindow` — useful only if the console window (or something else) happens to be covering it. Ignores `-w` entirely, the same way this frontend's own `coretop` already does.

## 4. Audio output — core-agnostic drain, per-frontend sink

The DSP mixing itself has been correct and complete since earlier work (`Venus_APU.md`) - `SDsp.GenerateSample` mixes all 8 voices plus echo/FIR and `AudioSettings.MasterVolume`, respecting `AudioSettings.AudioEnabled`/`Muted` (silence is still enqueued when either is off, not skipped - keeps buffer timing continuous), and enqueues interleaved 16-bit signed PCM stereo frames into `Spc700.Dsp.AudioBuffer` (a plain `Queue<short>`, capped at `AudioSettings.AudioBufferMaxSamples` - oldest samples drop once full) at `AudioSettings.SampleRate` (32kHz). What was missing for a long time was the connective piece: draining that queue into a real output device.

**`ICore.AudioSampleRate` / `ICore.DequeueAudioSamples(maxFrames)`** are the audio counterpart to `GetFrameBufferRgba()` - added specifically so a second frontend (`EmuSen.Mistress9`) adding real audio output didn't need its own Venus-specific access to duplicate the drain logic against. `DequeueAudioSamples` is destructive (removes exactly what it returns) and capped (never blocks, never returns more than asked, returns fewer or an empty array if less is buffered) - deliberately not the same shape as `IDebugTarget.GetAudioSamples()`, which is a non-destructive one-shot snapshot for `audiodump` WAV export, not a real-time drain. `VenusCore.DequeueAudioSamples` is a straight reshape of the drain loop that used to live inline in this frontend's own `PumpAudio` (see git history) - no new logic, same as `GetFrameBufferRgba()`'s own relationship to `Renderer`.

**`EmuSen.Hotaru/Audio/AudioPlayer.cs` and `EmuSen.Mistress9/Audio/AudioPlayer.cs`** are now the same class, duplicated rather than shared (matching this project's established Hotaru/Mistress9 non-sharing-UI precedent) — both go through SDL's queue-based audio API (`SDL_OpenAudioDevice`/`SDL_QueueAudio`, no callback), reusing the Silk.NET.SDL dependency `Input/GamepadManager.cs` already brings in for gamepad support in both projects. Hotaru's own copy is adapted for `ICore` directly (`Pump(ICore core)`) rather than Mistress9's `EmulatorSession` wrapper, which Hotaru has no equivalent of. Both call `core.DequeueAudioSamples(maxFrames)` (the same core-agnostic drain `ICore` exposes for exactly this - added originally so Mistress9 adding real audio output didn't need Venus-specific access to duplicate the drain logic against) and push the result via `SDL_QueueAudio`, throttled against a runaway backlog via `SDL_GetQueuedAudioSize` (skips pumping while more than two buffers' worth - `2 * BufferFrames`, 4096 frames each - is still unplayed), since SDL's queue always accepts more with no built-in readiness gate the way Raylib's old `IsAudioStreamProcessed` had. Called once per `RunFrame()` from the emulation thread in both frontends (not the UI thread - `SDL_QueueAudio` specifically is documented thread-safe, unlike the joystick/controller polling `GamepadManager` deliberately keeps pinned to the UI/init thread).

Raylib's own `AudioStream` pipeline (`PumpAudio`, `Raylib.SetAudioStreamBufferSizeDefault`/`LoadAudioStream`/`UpdateAudioStream`) is gone entirely along with the rest of Raylib in this frontend - see this doc's own top-of-file revision note.

**SDL subsystem lifecycle: `InitSubSystem`/`QuitSubSystem`, not `Init`/`Quit`, in both `AudioPlayer` and `GamepadManager`, in both frontends.** `SDL_Quit()` unconditionally shuts down the *entire* SDL library regardless of which subsystem asked for it - with two independent classes both touching SDL in the same process (gamepad polling, audio output), whichever disposed first via `Quit()` would have killed the other's still-open subsystem. `QuitSubSystem` is refcounted per-subsystem and doesn't have that problem.
